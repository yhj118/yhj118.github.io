# Intranet Groupware

<br>

## 1. 일정 기능 구현 목표

> 개인 일정과 공동 일정을 월간 달력에서 확인하고, 전자결재에서 승인된 휴가·출장을 작성자의 일정에 자동으로 반영한다.

달력에서 날짜를 선택하면 그날의 일정을 볼 수 있다. 직접 등록한 일정은 상세 모달에서 확인하고, 권한에 따라 수정·삭제할 수 있도록 구성했다. **달력, 선택한 날짜의 목록, 다가오는 일정**은 같은 데이터를 기준으로 그린다.

<br>

| 기술 | 일정 기능에서 맡은 역할 |
| --- | --- |
| Java 17 · Spring Boot · Spring MVC | 화면 요청 처리, JSON 요청을 `ScheduleRequest`로 변환, 일정 서비스 호출 |
| MariaDB · MyBatis | 로그인 사원 기준 조회, 일정 INSERT·UPDATE·DELETE |
| Thymeleaf | 조회 목록과 로그인 정보를 JavaScript로 전달, CSRF 토큰 출력 |
| HTML · CSS · Tabler | 월간 달력 레이아웃, 종류별 색상, 등록·수정·상세·삭제 모달과 알림 |
| 순수 JavaScript | 날짜 계산, 배열 가공, 달력 DOM 생성, 필터, `fetch()` 요청 |
| Spring Security | 로그인 확인과 변경 요청의 CSRF 토큰 검사 |
| Spring 트랜잭션 | 전자결재 승인 처리와 휴가·출장 일정 등록을 같은 작업으로 처리 |

<br>

## 2. 일정 테이블과 조회 범위

`schedule` 테이블에 일정 식별번호 `schedule_id`, 사원 식별번호 `employee_id`, 결재 문서 번호 `approval_id`, 일정 유형과 제목·내용·기간을 저장한다. 시작일과 종료일은 Java에서 `LocalDate`로 받는다. 날짜만 필요한 일정이므로 시·분은 입력하지 않는다.

<br>

| DB 유형 | 의미 | 조회 범위 |
| --- | --- | --- |
| `PERSONAL` | 사용자가 직접 등록한 개인 일정 | 본인 |
| `COMMON` | 전 직원에게 공개하는 공동 일정 | 로그인한 모든 사원 |
| `APPROVAL` | 승인된 휴가·출장에서 자동 생성된 일정 | 결재 문서를 작성한 사원 본인 |

<br>

개인·공동 일정은 연결할 결재 문서가 없으므로 `approval_id`를 비워 둔다. 휴가·출장 일정은 `approval_id`로 원본 결재 문서와 연결한다. **DB에 저장하는 유형**과 **화면에서 구분하는 종류**는 다르다. 예를 들어 휴가는 DB에서 `APPROVAL`이고, 화면에서는 `kind()`가 제목 `휴가`를 보고 `vacation`으로 분류한다.

<br>

`selectAllSchedule()`에서는 **내 개인·결재 일정**과 **공동 일정 전체**를 한 번에 가져온다. 아래는 조회 조건을 읽기 쉽게 정리한 SQL이다.

```sql
SELECT *
FROM schedule
WHERE (
    employee_id = #{employeeId}
    AND schedule_type IN ('PERSONAL', 'APPROVAL')
)
OR schedule_type = 'COMMON';
```

괄호 안의 사원 ID 조건은 개인·결재 일정에만 적용된다. 공동 일정은 작성자 ID와 관계없이 조회된다.

<br>

> **한 줄 요약**<br>
> 일정은 한 테이블에서 유형으로 구분하고, 서버에서 로그인한 사원이 볼 수 있는 데이터만 조회한다.

<br>

## 3. DB에서 달력 화면까지 데이터 전달

1. 브라우저에서 `GET /openSchedule`을 요청한다.
2. `ScheduleController`가 `loginEmployee`에서 사원 ID를 읽고, `ScheduleService`를 통해 `ScheduleMapper.selectAllSchedule()`을 호출한다.
3. MyBatis가 조회 결과를 `List<ScheduleResponse>`로 반환한다.
4. Controller가 `model.addAttribute("scheduleList", scheduleList)`로 데이터를 담고, `schedule/scheduleMain` 뷰를 반환한다.
5. Thymeleaf가 목록을 JavaScript에 전달하고 브라우저가 `render()`를 호출해 달력을 그린다.

<br>

`scheduleList`는 `th:inline="javascript"` 블록에서 `initialSchedules`로 받는다. 같은 블록에서 현재 사원 ID와 권한도 받는다. 이 값들은 최초 HTML 응답에 포함되므로, **처음 달력을 그릴 때 별도로 목록 API를 호출하지 않는다.**

```html
<script th:inline="javascript">
    const initialSchedules = /*[[${scheduleList ?: {}}]]*/ [];
</script>
```

`initialSchedules`는 서버에서 처음 받은 배열이다. 화면에서 사용할 `schedules`는 이 배열을 `map()`으로 복사해 만든다. `...item`으로 기존 필드를 가져오고, `Number(item.scheduleId)`로 일정 번호를 숫자로 맞춘다. 이후 수정·삭제는 이 화면용 배열을 갱신한다.

<br>

> **한 줄 요약**<br>
> `scheduleList`를 Thymeleaf로 받은 뒤, JavaScript의 `schedules` 배열로 만들어 달력에 표시한다.

<br>

## 4. 월간 달력 렌더링

### 날짜와 화면 상태

- `displayedMonth`: 현재 표시할 월을 가리킨다. 이전·다음 달 버튼과 월 선택 입력으로 변경한다.
- `selectedDate`: 사용자가 선택한 날짜다. 날짜를 클릭하면 목록과 선택 표시가 바뀐다.
- `activeFilters`: 현재 표시할 일정 종류를 `Set`으로 관리한다. 개인·공동·휴가·출장 버튼으로 표시 여부를 바꾼다.
- `editingId`와 `detailedId`: 수정 중이거나 상세에서 보고 있는 일정 번호를 각각 저장한다.

<br>

오늘 날짜는 `Intl.DateTimeFormat`에 `Asia/Seoul`을 지정해 계산한다. 날짜 키는 `localKey()`에서 연·월·일을 뽑아 `YYYY-MM-DD`로 만든다. 이 형식으로 자릿수가 맞춰져 있으면 문자열 비교로 기간 포함 여부를 확인할 수 있다. 날짜에 하루를 더하거나 월을 계산할 때는 `toDate()`로 연·월·일을 분리해 `Date` 객체를 만든다.

<br>

### 42개 날짜 칸 만들기

1. 표시할 월의 1일을 구하고, 그 주의 일요일까지 이동한다.
2. 하루씩 이동하며 **7열 × 6행, 총 42개** 날짜 칸을 만든다. 이전·다음 달 날짜도 빈칸 대신 채운다.
3. 각 날짜에 대해 **시작일 ≤ 해당 날짜 ≤ 종료일**인 일정을 찾는다. 여러 날에 걸친 일정도 해당하는 모든 날짜에 표시한다.
4. 칸에는 일정 버튼을 최대 3개까지 보여준다. 더 있으면 `+N개 더보기`를 표시하고, 클릭하면 선택 날짜 목록에서 전체 일정을 볼 수 있다.
5. 날짜 칸을 `DocumentFragment`에 모은 뒤 `replaceChildren()`으로 달력 칸을 한 번에 교체한다.

<br>

아래는 달력에 표시할 일정을 고르는 부분이다. 종료일도 포함하기 때문에 11월 3일~5일 일정은 **3일·4일·5일**에 모두 표시된다.

```js
const items = events.filter(
    item => item.scheduleStart <= key && item.scheduleEnd >= key
);
```

선택한 종류와 조회 조건에 맞는 일정만 사용한다. 일정 제목과 본문은 `textContent`로 넣고, `kind-personal`, `kind-common`, `kind-vacation`, `kind-trip` 같은 CSS 클래스로 색을 구분했다. 달력 칸에는 오늘·선택 날짜 표시와 키보드로 조작할 수 있는 버튼을 둔다.

<br>

### 월간 건수, 선택 날짜, 다가오는 일정

| 영역 | 표시 기준 |
| --- | --- |
| 월간 일정 수 | 일정 기간이 표시하는 월과 겹치는 건수. 여러 날짜에 보이는 한 일정도 한 건으로 센다. |
| 선택한 날짜 | 선택 날짜를 포함하는 모든 일정. 목록에서 제목을 누르면 상세 모달을 연다. |
| 다가오는 일정 | 종료일이 오늘 이후이거나 오늘인 일정 중 최대 5건. 이미 시작한 일정은 오늘을 기준으로 정렬한다. |

<br>

월 이동, 오늘 버튼, 날짜 선택, 유형 필터는 페이지에 이미 내려받은 `schedules`로 처리한다. 이런 조작에는 추가 DB 조회가 없다.

<br>

> **한 줄 요약**<br>
> 날짜 칸을 만들고 일정의 기간을 비교해 배치한 뒤, 같은 배열로 달력과 오른쪽 목록을 갱신한다.

<br>

## 5. 일정 상세·등록·수정·삭제

### 상세와 모달 전환

`openDetail(id)`는 `schedules.find()`로 일정 번호가 같은 항목을 찾는다. 제목, 기간, 내용을 상세 모달에 채우고, 유형에 따라 안내 문구와 수정·삭제 버튼을 바꾼다. 상세 데이터는 이미 조회한 배열에서 가져온다.

<br>

등록·수정은 같은 폼을 사용한다. `prepareForm(null)`은 선택 날짜를 기본값으로 넣고, `prepareForm(item)`은 기존 데이터를 채운다. 수정할 때는 유형 선택을 비활성화한다. 상세에서 수정 또는 삭제 확인으로 넘어갈 때는 `hidden.bs.modal` 이벤트를 한 번만 받아 **기존 모달이 닫힌 후 다음 모달을 연다.**

<br>

### JSON 요청과 CSRF 처리

폼을 제출할 때 `preventDefault()`로 기본 페이지 이동을 막는다. 브라우저에서 제목이 비어 있는지, 시작·종료일이 맞는지, 현재 화면에서 선택할 수 있는 유형인지 검사한다. 시작일을 바꾸면 종료일의 최소값도 함께 갱신한다.

<br>

`fetch()`에 `Content-Type: application/json`을 설정하고 `JSON.stringify()`로 입력값을 보낸다. Thymeleaf가 HTML의 메타 태그에 넣어 둔 **CSRF 토큰과 헤더 이름**을 읽어 변경 요청의 헤더에 추가한다. 서버는 `@RequestBody ScheduleRequest`로 JSON을 받고, 사원 ID는 JSON이 아니라 로그인 정보에서 가져온다.

<br>

| 작업 | HTTP 요청 | 성공 후 화면 처리 |
| --- | --- | --- |
| 등록 | `POST /insertSchedule` | 페이지를 다시 열어 DB에서 발급된 일정 ID를 포함한 목록을 가져온다. |
| 수정 | `POST /updateSchedule` | 같은 ID의 항목을 `map()`으로 바꾸고, 변경한 시작일로 이동해 다시 그린다. |
| 삭제 | `POST /deleteSchedule` | 확인 모달에서 실행하며, 성공하면 `filter()`로 해당 항목을 빼고 다시 그린다. |

<br>

HTTP 오류가 나면 알림을 표시한다. 삭제는 상세 모달에서 바로 실행하지 않고, 별도 확인 모달을 거친다.

<br>

### 등록 직후에는 왜 새로고침하는가?

일정 등록 응답은 생성된 ID 대신 `OK` 문자열을 반환한다. 브라우저에서 만든 임시 번호를 배열에 그대로 넣으면, 등록 직후 그 항목을 수정·삭제할 때 DB의 실제 `schedule_id`와 일치하지 않는다. 그래서 **등록에 성공하면 `window.location.reload()`로 다시 조회**해 실제 ID를 받도록 했다. 수정·삭제는 이미 실제 번호를 가지고 있으므로, 응답이 성공한 뒤 배열을 바꾸는 것으로 화면을 갱신할 수 있다.

<br>

> **한 줄 요약**<br>
> 등록은 실제 ID를 다시 조회하고, 수정과 삭제는 그 ID를 기준으로 브라우저의 목록을 갱신한다.

<br>

## 6. 공동 일정과 권한

공동 일정은 캘린더에서 개인 일정과 다른 색으로 보여주고, 전 사원이 조회할 수 있다. 화면에서는 로그인 사원의 `role`이 `ADMIN`일 때만 공동 일정 등록 옵션을 사용할 수 있다. `canEdit()`에서는 개인 일정의 소유자를 확인하고, 공동 일정은 관리자에게만 수정·삭제 버튼을 표시한다. 승인 연동 일정은 버튼을 숨긴다.

<br>

**화면에서 버튼을 숨기는 것과 서버에서 요청을 거부하는 것은 다르다.** 현재 SQL의 수정 조건은 일정 번호·로그인 사원 ID·일정 유형을 확인한다. 따라서 공동 일정도 다른 관리자가 만든 건 SQL의 작성자 조건에 맞지 않는다. 등록·삭제 경로에 서버 쪽 역할·유형 검사까지 적용하는 부분은 아래 개선 방향에 따로 정리했다.

<br>

## 7. 전자결재 승인과 일정 연동

휴가 신청서나 출장 계획서를 승인하면 `EAService.updateApprovalStatus()`에서 승인된 문서의 기간을 조회한다. 문서 종류가 휴가·출장에 해당하지 않으면 일정 생성 없이 종료한다.

<br>

1. `selectScheduleData()`에서 문서 번호, 작성자 사원 ID, 휴가 또는 출장의 시작일·종료일을 읽는다.
2. `ScheduleRequest`에 `approvalId`, `scheduleType = "APPROVAL"`, 제목 `휴가` 또는 `출장`, 기간을 넣는다.
3. `scheduleService.insertSchedule()`에 **결재자가 아닌 문서 작성자의 ID**를 전달한다.
4. 작성자가 달력에 접속하면 자신의 `APPROVAL` 일정이 조회된다. 상세에는 전자결재에서 자동 반영됐다는 문구를 표시한다.

<br>

결재 상태 변경과 일정 INSERT는 같은 `@Transactional` 서비스 메서드 안에서 수행한다. 일정 저장 중 롤백 대상 예외가 발생하면 결재 상태 변경도 함께 롤백된다. 달력 화면 안내에 품의서가 적혀 있지만, 현재 승인 연동 SQL이 처리하는 양식은 **휴가와 출장**이다.

<br>

### 외래키 오류를 해결한 과정

자동 등록 시 `schedule.approval_id`가 존재하는 결재 문서를 가리켜야 한다. 연동 데이터에서 원본 문서 번호를 누락하면 올바른 ID를 일정에 넣을 수 없다. 승인 데이터 조회에 **`ea.approval_id`를 포함**하고, 조회 결과를 `ScheduleRequest.approvalId`에 넣어서 원본 문서와 연결했다.

<br>

> **한 줄 요약**<br>
> 승인된 휴가·출장의 날짜와 문서 ID를 가져와 작성자의 달력에 자동으로 저장한다.

<br>

건수와 목록의 조회 조건이 서로 다르다. 예를 들어 11월 5일에 시작하는 일정은 11월 3일 기준 **오늘 일정 건수에는 없지만**, 종료되지 않은 일정 목록에는 들어갈 수 있다.

<br>

## 주요 이슈 및 개선 방향

### 1. 공동 일정과 결재 연동 일정의 권한을 서버에서 검사하기

일반 등록 API는 요청으로 받은 일정 유형을 서비스에 전달한다. 따라서 `COMMON`은 관리자만 등록할 수 있고 `APPROVAL`은 결재 연동으로만 생성할 수 있다는 규칙을 서버에서 명시할 필요가 있다. 삭제 SQL도 요청의 `scheduleType`과 일치하는지 확인할 뿐 `APPROVAL`을 직접 제외하지 않는다. **저장된 유형·소유자·로그인 역할을 서버에서 함께 확인**하면 화면을 거치지 않은 요청에도 같은 규칙이 적용된다. 공동 일정은 작성한 관리자만 관리할지, 모든 관리자가 관리할지도 정한 뒤 SQL 조건을 맞춘다.

<br>

### 2. 실제 변경 결과와 생성된 일정 ID를 응답으로 돌려주기

현재 등록·수정·삭제 API는 `OK`를 반환하고 Mapper는 처리 건수를 반환하지 않는다. 조건에 맞는 행이 없어 수정·삭제가 되지 않아도, 화면은 성공으로 판단해 목록을 바꿀 수 있다. 변경 건수를 확인하고 결과에 맞는 HTTP 상태를 반환하도록 보완한다. 등록은 MyBatis에서 생성 키를 받아 응답에 포함하면, 새로고침 없이 실제 ID로 새 일정을 추가할 수 있다.

<br>

### 3. 날짜와 화면 안내의 기준 맞추기

달력의 오늘은 `Asia/Seoul` 기준이고 메인 페이지는 DB의 `CURDATE()`를 사용한다. 서버와 DB의 날짜 기준을 확인해 자정 전후에도 같은 날짜를 보여주도록 한다. 실제 목록이 오늘 이후의 일정도 포함한다면 제목을 `다가오는 일정`으로 맞추고, 결재 연동 안내도 실제 지원하는 **휴가·출장**으로 맞춘다.

<br>

## 구현 결과

**일정 조회 → 월간 달력 표시 → 상세보기 → 등록·수정·삭제** 흐름을 한 화면에서 처리하도록 구현했다. 개인 일정과 공동 일정에 서로 다른 조회 조건을 적용하고, 승인된 휴가·출장은 원본 결재 문서와 연결해 달력에 표시했다.

<br>

이 기능을 만들면서 **DB 조회 결과가 Thymeleaf를 거쳐 JavaScript 배열이 되고, 배열의 데이터가 실제 DOM으로 그려지는 과정**을 정리할 수 있었다. 새 일정을 수정·삭제하려면 화면에서 만든 임시 번호가 아니라 **DB가 발급한 식별번호**가 필요하다는 점도 확인했다.
