# Intranet Groupware

<br>

## 1. 전자결재 구현 목표

> 사원이 양식을 선택해 문서를 작성하고, 같은 팀의 결재자가 승인하거나 반려할 수 있도록 한다.

전자결재 화면에서 **내가 작성한 문서와 내가 결재할 문서**를 조회한다. 작성자는 결재 대기 문서를 수정하거나 삭제할 수 있고, 작성자와 결재자는 승인된 문서를 엑셀로 내려받을 수 있다. 휴가·출장 문서는 승인 시 작성자의 일정에도 등록된다.

<br>

| 기술 | 전자결재에서 맡은 역할 |
| --- | --- |
| Java 17 · Spring Boot · Spring MVC | 입력 폼 바인딩, 화면과 파일 응답, 서비스 로직과 트랜잭션 처리 |
| Spring Security | 로그인 인증. 서버에서 확인한 사원 식별번호를 기준으로 문서별 권한 검사 |
| MariaDB · MyBatis | 공통 문서와 양식별 상세 데이터 조회·저장, 생성 키 연결, 상태별 집계 |
| Thymeleaf · Tabler · JavaScript | 작성·상세·수정 폼, 결재 목록 모달, 검색·필터, 구매 물품 동적 입력 |
| MultipartFile · Java NIO | 첨부파일 저장, 다운로드 및 실제 파일 정리 |
| Apache POI | 승인된 문서를 양식별 `.xlsx` 파일로 생성 |

<br>

## 2. 테이블과 양식 설계

양식마다 항목이 달라도 **작성자, 결재자, 문서 종류, 결재 상태, 작성·수정·처리 일시, 결재 의견**은 공통이다. 공통 항목은 `electronic_approval`에 두고, 양식별 내용은 별도 테이블에 저장했다.

<br>

| 양식 | `ea_type` | 상세 테이블 | 주요 입력 |
| --- | --- | --- | --- |
| 기안서 | `PROPOSAL` | `ea_proposal` | 제목, 기안 목적, 내용 |
| 품의서 | `APPROVAL_REQUEST` | `ea_approval_request` | 제목, 품의 사유, 집행 예정일, 총액 |
| 휴가 신청서 | `VACATION` | `ea_vacation` | 휴가 종류, 시작일·종료일, 사유 |
| 출장 계획서 | `BUSINESS_TRIP` | `ea_business_trip` | 제목, 목적지, 기간, 교통수단, 비용 |
| 경위·시말서 | `FACT_REPORT` | `ea_fact_report` | 발생 일시와 장소, 경위, 원인, 재발 방지 대책 |
| 업무 보고서 | `WORK_REPORT` | `ea_work_report` | 보고일, 업무 기간, 개요, 진행 내용, 성과 |

<br>

공통 문서를 저장할 때 `ea_type`으로 양식 하나를 정하고, **그 양식의 상세 행 한 건**을 `approval_id`로 연결한다. 한 문서에 첨부파일은 여러 개 올릴 수 있으므로 `approval_attachment`는 문서와 **1:N** 관계다. 품의서는 `ea_approval_request_item`에 구매 물품을 여러 행으로 저장하며, 각 물품은 공통 문서 ID가 아닌 **품의서 ID인 `approval_request_id`**에 연결된다.

<br>

> **한 줄 요약**<br>
> 결재 상태는 공통 문서에서 관리하고, 서로 다른 입력 항목은 해당 양식의 상세 테이블에 저장한다.

<br>

## 3. 문서 작성

1. `/openFormSelect`에서 양식을 선택한다. 각 작성 화면에서 사원·팀·상위 부서 정보를 조회해 양식에 표시한다.
2. 폼을 제출하면 Spring MVC가 입력값을 `@ModelAttribute EARequest`로 받는다. 서버에서 확인한 `loginEmployee`의 `employeeId`를 작성자 ID로 사용한다.
3. `EAService`가 `findLevel5()`로 작성자와 같은 팀에서 직급이 `lv5`인 사원을 찾아 결재자로 설정한다.
4. `insertApproval()`로 공통 문서를 먼저 등록한 뒤, 해당 양식의 상세 데이터를 저장한다. 품의서에는 구매 물품을, 첨부를 지원하는 양식에는 선택한 파일을 추가로 저장한다.
5. 저장이 끝나면 `redirect:/openEAMain`으로 이동해 전자결재 목록을 다시 조회한다.

<br>

### 공통 문서 ID를 상세 테이블에 전달

공통 문서의 `approval_id`는 DB에서 자동 생성되므로, 저장하기 전에는 상세 테이블에 넣을 값을 알 수 없다. MyBatis의 `useGeneratedKeys`와 `keyProperty`를 사용하면 INSERT 후 생성된 키가 요청 객체에 들어온다.

```xml
<insert id="insertApproval"
        keyColumn="approval_id"
        useGeneratedKeys="true"
        keyProperty="approvalId">
    INSERT INTO electronic_approval (
        writer_employee_id, approver_employee_id, ea_type
    ) VALUES (
        #{employeeId}, #{approverEmployeeId}, #{eaType}
    )
</insert>
```

이후 양식별 INSERT가 `params.approvalId`를 사용한다. 품의서는 상세 행의 `approval_request_id`도 같은 방식으로 받아 구매 물품 행에 전달한다. 공통 문서와 상세 데이터 저장은 서비스의 `@Transactional` 안에서 처리한다.

<br>

### 품의서 구매 물품과 금액 계산

화면에서는 JavaScript로 구매 물품 행을 추가·삭제한다. 행의 입력 이름을 `items[0].itemName`, `items[0].itemAmount`처럼 구성하고, 행이 삭제되면 인덱스를 다시 맞춰 `List<EARequestItem>`으로 바인딩되도록 했다.

<br>

화면의 합계는 입력 중 확인하는 용도다. 서버에서도 구매 물품 유무, 물품명, 금액을 확인하고 **각 물품 금액을 합산해 총액을 다시 계산**한다. 최종 총액은 1억 원 이하로 제한한다. 품의서 상세 행을 저장한 뒤 MyBatis의 `<foreach>`로 물품을 한 번에 INSERT한다.

<br>

> **한 줄 요약**<br>
> 로그인 사원과 같은 팀의 결재자를 연결한 뒤, 공통 문서에서 생성한 ID를 사용해 양식과 하위 데이터를 저장한다.

<br>

## 4. 결재 현황과 문서 목록

### 상태별 건수 집계

`countApprovalStatus()`에서 로그인 사원이 **작성자인 문서**와 **결재자인 문서**를 구분해 대기(`PENDING`)·승인(`APPROVE`)·반려(`REJECT`) 건수를 계산한다. `COUNT(CASE WHEN ... THEN 1 END)`을 사용해 여러 조건의 건수를 한 번의 조회로 받는다.

```sql
COUNT(
    CASE WHEN approval_status = 'PENDING'
          AND approver_employee_id = #{employeeId}
         THEN 1
    END
) AS count_approval_pending
```

예를 들어 위 식은 로그인 사원이 결재자로 지정된 문서 중 아직 대기 상태인 건만 센다.

<br>

### 다른 양식의 제목을 한 컬럼으로 조회

기안서는 `proposal_title`, 품의서는 `approval_request_title`처럼 테이블마다 제목 컬럼 이름이 달랐다. 목록 쿼리에서 문서 종류별 상세 테이블을 `LEFT JOIN`하고, `COALESCE()`로 처음 나온 `NULL`이 아닌 제목을 공통 컬럼 `title`로 받았다.

```sql
COALESCE(
    proposal.proposal_title,
    request.approval_request_title,
    work.work_report_title,
    fact.fact_report_title,
    business.business_trip_title
) AS title
```

휴가 신청서에는 별도 제목이 없어 `EAResponse.getEATitle()`에서 `휴가 신청서`를 반환한다. 목록에는 **내가 작성했거나 나에게 결재가 지정된 문서**만 포함한다. 작성일시 내림차순으로 정렬하고, 작성일시가 같으면 문서 ID 내림차순으로 정렬한다.

<br>

### 대기·승인·반려 영역과 전체보기

Service에서는 목록을 한 번 순회하며 상태별로 나눈다. 메인 화면은 상태별 최신 **최대 10건**을 보여주고, 조회한 전체 목록은 모달에서 사용한다.

| `Map<String, List<EAResponse>>`의 키 | 사용 위치 |
| --- | --- |
| `pendingList` | 결재 대기 목록 |
| `approveList` | 승인 문서 목록 |
| `rejectList` | 반려 문서 목록 |
| `dataAllList` | 전체보기 모달에서 사용할 전체 행 |

<br>

Thymeleaf의 `th:each`로 표를 만들고, 각 행에 상태와 양식을 `data-status`, `data-type`으로 넣었다. 사용자가 전체보기를 누르면 선택한 상태의 행만 표시한다. 양식 선택과 검색어를 함께 적용하고, **제목·기안자·결재자** 중 일치하는 내용이 있는지 브라우저에서 찾는다. 검색 결과 건수와 빈 목록 안내도 갱신한다. 결재 대기 목록에는 처리일 컬럼을 숨긴다.

<br>

> **한 줄 요약**<br>
> 양식마다 다른 제목을 하나로 모아 조회하고, 결과를 상태별 10건과 전체보기 목록으로 나눠 사용한다.

<br>

## 5. 문서 상세 조회와 모달

목록에서 문서를 선택하면 `approvalId`와 `keyType`을 `GET /viewApprovalDetail`에 전달한다. MyBatis의 `<choose>`로 양식별 상세 테이블을 조회하고, SQL에서 로그인 사원이 **해당 문서의 작성자 또는 지정 결재자**인지 확인한다. 품의서에는 구매 물품 목록을, 첨부를 지원하는 양식에는 파일 목록을 추가로 조회한다.

<br>

같은 상세 요청이라도 접근 방식에 따라 반환 범위가 달라진다.

| 요청 방식 | 응답 |
| --- | --- |
| 상세 링크로 직접 접속 | 양식에 맞는 전체 HTML 페이지 |
| 모달에서 `fetch()` 호출 | 양식별 Thymeleaf `detail` 프래그먼트 |

<br>

모달 요청에는 `X-Requested-With: XMLHttpRequest` 헤더를 넣는다. Controller는 이 값이 있으면 `viewName + " :: detail"`을 반환한다. 브라우저는 응답을 HTML로 받아 모달의 상세 영역에 넣기 때문에 목록 페이지를 다시 열지 않고 문서를 확인할 수 있다.

<br>

상세를 불러오는 동안 로딩 메시지를 보여주고, `response.ok`와 리다이렉트 여부를 확인해 오류를 안내한다. `AbortController`로 이전 요청이나 오래 걸리는 요청을 중단한다. 목록으로 돌아갈 때는 기존 스크롤 위치와 선택한 링크의 포커스를 복원한다. 전체보기 UI는 HTML `<dialog>`로 열고 닫는다.

<br>

> **한 줄 요약**<br>
> 문서 ID와 양식으로 상세 데이터를 찾고, 모달에서는 필요한 HTML 조각만 가져와 기존 목록 위에서 보여준다.

<br>

## 6. 문서 수정과 삭제

### 작성자와 대기 상태를 서버에서 확인

**작성자 본인의 결재 대기 문서**만 수정·삭제할 수 있다. 수정 화면을 열 때도 검사하지만, 화면의 버튼 노출 여부만으로 권한을 결정하지 않는다. 저장·삭제 요청이 들어오면 서비스에서 문서를 다시 조회해 작성자와 상태를 확인한다.

```sql
SELECT approval_id, writer_employee_id, ea_type, approval_status
FROM electronic_approval
WHERE approval_id = #{approvalId}
FOR UPDATE;
```

`FOR UPDATE`는 트랜잭션이 끝날 때까지 대상 문서 행을 잠근다. 그동안 다른 요청이 같은 행을 변경하는 작업은 대기하게 된다. 수정·삭제할 상세 테이블은 브라우저가 보낸 값 대신 **DB에서 조회한 `ea_type`**으로 결정한다.

<br>

### 수정

1. `/openUpdateApproval`에서 양식에 맞는 수정 폼을 열고 기존 값을 표시한다. 모달에서는 `edit` 프래그먼트를 사용한다.
2. `POST /updateApproval`로 제출하면 양식별 필수 입력, 기간의 시작·종료 순서, 금액 등을 서버에서 검사한다.
3. 품의서는 서버가 총액을 다시 계산하고, 해당 품의서의 기존 물품 행을 삭제한 뒤 수정된 목록을 저장한다.
4. 삭제 선택을 하지 않은 첨부는 유지하고, 선택한 첨부만 제거한다. 새로 선택한 파일은 추가한다.
5. 공통 문서의 `approval_update_at`을 갱신하고 목록으로 돌아간다.

<br>

수정 폼에서는 공통 스크립트 `approval-edit.js`로 물품 행의 인덱스, 금액 표시, 기간 입력, 새 첨부파일 목록을 관리했다. 모달에 나중에 삽입되는 폼에도 동작하도록 상위 요소에서 이벤트를 받아 처리한다.

<br>

### 삭제

`POST /deleteApproval`에서 작성자와 대기 상태를 다시 확인한다. 첨부파일 DB 행과 품의서 구매 물품처럼 공통 문서나 상세 양식을 참조하는 데이터를 먼저 지운다. 이후 **양식 상세 행 → 공통 문서 행** 순서로 삭제한다. 최종 삭제 건수가 예상과 다르면 충돌 오류를 반환하고 DB 변경을 롤백한다.

<br>

> **한 줄 요약**<br>
> 서버에서 문서 상태와 작성자를 다시 확인한 후, 수정은 해당 양식에 반영하고 삭제는 외래키를 참조하는 자식 데이터부터 처리한다.

<br>

## 7. 첨부파일 저장과 다운로드

기안서·품의서·경위/시말서·업무 보고서에서 여러 첨부파일을 올릴 수 있다. 폼은 `multipart/form-data`로 보내고 서버는 `List<MultipartFile>`로 받는다. 휴가 신청서와 출장 계획서는 첨부파일을 사용하지 않는다.

<br>

### 실제 파일과 DB 메타데이터를 분리

- 허용 확장자는 `jpg`, `jpeg`, `pdf`, `zip`이다. 새로 선택한 파일을 먼저 검사한 뒤 저장한다.
- 실제 파일은 `uploads/approval/`에 UUID 이름으로 저장한다. DB에는 문서 ID, 원래 파일명, 저장 파일명, 경로, 파일 유형과 크기를 남긴다.
- `/downloadAttachment`는 첨부 ID와 로그인 사원의 문서 접근 권한을 확인한다. 실제 파일이 있고 읽을 수 있으면 `FileSystemResource`로 응답하고, `Content-Disposition`에 원래 파일명을 지정한다.

<br>

### DB가 롤백되면 실제 파일은 어떻게 되는가?

DB 트랜잭션은 서버 폴더에 저장한 파일을 자동으로 되돌리지 않는다. 예를 들어 새 파일 저장 이후 DB INSERT가 실패하면, DB 기록은 없어져도 폴더에는 파일이 남을 수 있다. 반대로 기존 파일을 먼저 지운 뒤 DB가 롤백되면, DB에는 기록이 남아 있는데 다운로드할 파일은 사라진다.

<br>

이를 줄이기 위해 `EAServiceAttachment`에서 트랜잭션 완료 시점에 파일을 정리한다.

| 상황 | 실제 파일 처리 |
| --- | --- |
| 새 파일 저장 후 DB 롤백 | `afterCompletion()`에서 롤백을 확인하고 이번에 저장한 파일을 삭제 |
| 기존 파일 삭제 또는 문서 삭제 | DB 커밋이 끝난 뒤 `afterCommit()`에서 기존 파일을 삭제 |

<br>

첨부파일 서비스는 `Propagation.MANDATORY`로 문서 작성·수정·삭제 트랜잭션에 참여한다. 기존 파일을 제거할 때는 첨부 ID가 해당 문서에 속하는지 확인하고, 파일 경로도 지정된 저장 폴더 아래인지 확인한다. 커밋 후 실제 파일 삭제가 실패하면 로그를 남긴다.

<br>

> **한 줄 요약**<br>
> 첨부파일은 디스크에, 파일 정보는 DB에 저장하고, 커밋과 롤백 시점을 구분해 남는 파일을 정리한다.

<br>

## 8. 승인·반려와 일정 연동

지정된 결재자가 대기 문서를 열면 승인·반려 버튼이 보인다. 버튼을 누르면 `POST /updateStatus`로 문서 ID, 처리 상태와 의견이 전달된다. SQL은 **문서 ID와 결재자 ID**를 조건으로 상태, 결재 의견, 처리 일시를 갱신한다.

<br>

문서 갱신이 성공했고 결과가 `APPROVE`이면, `selectScheduleData()`에서 그 문서가 **휴가 또는 출장 양식**인지 확인한다. 해당하는 경우에만 시작일과 종료일을 읽어 일정을 저장한다.

1. 휴가·출장 문서에서 `approval_id`, `writer_employee_id`와 기간을 조회한다.
2. `ScheduleRequest`에 원본 문서 ID와 `scheduleType = "APPROVAL"`을 넣는다.
3. 양식에 따라 일정 제목을 `휴가` 또는 `출장`으로 정하고, 문서의 시작일과 종료일을 넣는다.
4. `scheduleService.insertSchedule()`에 **결재자가 아닌 문서 작성자의 ID**를 전달한다.

<br>

결재 상태 갱신과 일정 저장은 같은 `@Transactional` 서비스 메서드 안에서 진행한다. 일정이 정상 등록되면 작성자의 달력에 보인다. 달력 UI는 승인 연동 일정을 직접 수정할 수 있는 개인 일정과 구분해 표시한다. 반려되거나 다른 양식이 승인되면 일정은 등록하지 않는다.

<br>

> **한 줄 요약**<br>
> 휴가나 출장 문서가 승인되면, 문서에 기록된 기간을 작성자의 일정에 자동으로 등록한다.

<br>

## 9. 승인 문서 엑셀 다운로드

`/downloadProposalExcel`에서 문서 ID와 양식을 받는다. 경로 이름에는 Proposal이 들어가지만, 현재 구현은 **6종 양식 모두** 지원한다. 서버에서 **승인된 문서인지, 로그인 사원이 작성자 또는 지정 결재자인지** 확인한 뒤 파일을 생성한다.

<br>

`EAServiceExcel`은 Apache POI의 `XSSFWorkbook`으로 양식에 맞는 시트를 만든다. 작성자 정보, 본문, 결재 상태와 의견을 넣고, 품의서에는 구매 물품과 총액을, 첨부 양식에는 파일 목록을 추가한다. 날짜·숫자 형식, 셀 병합과 스타일, 인쇄 범위를 적용해 문서 형태로 출력한다.

<br>

워크북을 `ByteArrayOutputStream`에 쓰고, 생성한 바이트 배열을 `ResponseEntity<byte[]>`로 내려준다. 파일명은 `양식명_문서ID.xlsx` 형식이다. 첨부파일은 파일 목록으로만 표시하며, 원본 파일 자체는 별도 다운로드 기능으로 받는다.

<br>

> **한 줄 요약**<br>
> 승인 여부와 문서 접근 권한을 확인한 뒤, 양식별 데이터를 서버에서 엑셀 파일로 만들어 반환한다.

<br>

## 주요 이슈 및 개선 방향

### 1. 결재 상태 전이를 서버에서도 제한하기

현재 화면은 지정 결재자에게만 대기 문서의 승인·반려 버튼을 보여준다. 다만 상태 변경 SQL에는 결재자 조건만 있고, **현재 상태가 `PENDING`인지 검사하는 조건은 없다.** 서버에서 허용할 결과를 `APPROVE`와 `REJECT`로 제한하고, 갱신 조건에 `AND approval_status = 'PENDING'`을 추가하면 이미 처리한 문서를 다시 변경하는 요청을 막을 수 있다. 일정에도 원본 문서 ID를 기준으로 중복 등록을 막는 규칙을 둘 수 있다.

<br>

### 2. 팀별 결재자 선정 기준 명확히 하기

현재 조회는 같은 팀에서 `lv5` 사원 한 명이 반환된다는 전제다. 같은 팀에 해당 사원이 없거나 여러 명이면 작성 단계에서 문제가 생길 수 있다. 팀별 결재자를 명시적으로 설정하거나, 지정되지 않은 경우 사용자에게 안내하는 방식으로 보완할 수 있다.

<br>

### 3. 첨부파일 접근 경로 통일하기

다운로드 API에서는 문서 작성자와 결재자 조건을 검사한다. 프로젝트의 공통 정적 리소스 설정은 `/uploads/**`를 제공하므로, **결재 첨부 폴더가 그 범위에 포함되지 않도록** 프로필 이미지 경로와 분리하는 것이 좋다. 결재 첨부파일은 문서별 권한을 검사하는 다운로드 API를 통해서만 내려주는 구조로 정리할 수 있다.

<br>

## 구현 결과

전자결재 한 화면에서 **6종 양식 작성, 대기·승인·반려 목록 조회, 상세보기, 수정·삭제, 승인·반려, 첨부와 엑셀 다운로드**를 처리하도록 구성했다. 휴가·출장 승인 결과를 일정으로 연결하면서, 결재 기능에서 저장한 데이터가 다른 화면에서 다시 활용되도록 구현했다.

<br>

이 기능을 만들면서 **생성된 키로 여러 테이블을 연결하는 방법**, **서버에서 작성자와 결재자의 권한을 구분하는 방법**, 그리고 **DB 트랜잭션과 파일 시스템의 저장 시점을 맞추는 방법**을 정리했다.
